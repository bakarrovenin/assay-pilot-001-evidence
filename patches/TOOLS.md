# Tools and versions (protocol section 2)

The harness never calls a fixer. Each patch is a diff supplied on disk at
`patches/<finding>/<tool>.patch`, and the tool column in the report is the
diff's filename. This file pins what produced each one, with the date, so the
numbers are reproducible and the illustrative cells are not mistaken for
vendor output.

## Illustrative (written by us, not vendor output)

- `fixer-01`, `fixer-02`, `fixer-03` on finding-01. Written during the manual
  run (protocol section 7) to exercise the four checks: a correct fix, a
  string-match fix, and a suppression-in-effect fix. These are ours, not any
  vendor's, and finding-01 is deliberately the easiest shape.

## Illustrative probes (written by us to validate the checks)

- `lazy-string-match` and `lazy-suppression` on findings 04 and 13. Built in
  the style of finding-01's fixer-02 and fixer-03 to answer one question: check
  B passed on all five real patches, which is the opposite of what the thesis
  predicts, so were the held-out sets actually able to catch a lazy fix on
  these shapes? `lazy-string-match` blocks the reported payload literally and
  leaves the flaw. `lazy-suppression` moves the query build into a helper that
  concatenates instead of interpolating, which closes the Semgrep alert without
  touching the hole. Both scored NOT VERIFIED on both findings; check B caught
  every one, and on the two suppression patches, where check A passed, B was
  the only check that could. The shapes discriminate. See the Phase C
  experiment write-up.

## Blind re-run (stripped corpus, note 12)

Tool keys carry the suffix `-blind` so a blind cell never merges with the
provisional cell of the same tool in the matrix, and the two can be read side
by side in the report.

- `copilot-autofix-blind`: **GitHub Copilot Autofix**, engine **CodeQL
  Default setup**, **CodeQL 2.27.0**, default suite, threat model remote,
  2026-09-14, handoff set-c, one throwaway public repo per finding
  (`bakarrovenin/assay-autofix-blind-finding-{04,08,13}`). Findings 04 and 08
  raised `py/sql-injection` at the sink; neither fix auto-generated, both
  required an explicit generate request (POST autofix), then were committed
  to an `autofix-suggestion` branch and diffed against main. Finding 13 raised
  **no alert** (43 rules, 0 results), reproducing the Phase C no-alert on the
  stripped module: `results/finding-13/copilot-autofix-blind.no-alert.json`.

- `chatgpt-blind`: **ChatGPT**, model **ChatGPT Think**, 2026-09-14, handoff
  set-a, findings 01, 04, 08 and 13. Each given only that finding's bundle and
  the fixed prompt. The returned fixes were written into the stripped originals
  by us, exactly as returned, and diffed against the committed baseline.

- `claude-code-blind`: **Claude Code v2.1.270**, model **Opus 5**
  (`claude-opus-5`), 2026-09-14, handoff set-d, findings 01, 04, 08 and 13.
  One fresh session per finding, started in that finding's bundle directory,
  with the bundle's `PROMPT.txt` line as the first and only human message;
  version and model are read from each session's own record, which also shows
  one human turn and a working directory confined to the bundle. The tool
  patched the bundle file in place; the diffs here were regenerated by us with
  `git diff` against the committed originals, and the `finding-08.patch` file
  the tool left in that bundle was not used.

## Provisional: every patch on findings 04, 08 and 13

Every patch on findings 04, 08 and 13, real and probe, was cut against a
module whose docstring named the shape, the sink and the fix
(METHODOLOGY-NOTES.md note 12). The modules were stripped on 2026-09-14 and
these diffs no longer apply to them: a `--rescore` reports INSUFFICIENT
EVIDENCE, not a verdict. They are kept as produced. The nine real-tool diffs
each delete the "this is the flaw" comment above the sink, so that comment
is visible in them as removed lines. The evidence they produced stands as a
dry run of the harness and not as a measurement of any tool, until the blind
re-run on the stripped corpus.

## Not a vendor comparison

Two or three scored cells per real tool, on four of fifteen findings, one
prompt each. That is enough to show the four checks separate a correct fix
from a lazy one. It is not a rate that generalises to any tool or codebase,
and it is not published as one.
